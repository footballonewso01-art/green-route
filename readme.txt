========================================================================
                      LINKTERY - АРХИТЕКТУРА И ДОКУМЕНТАЦИЯ
========================================================================

Данный файл содержит описание архитектуры проекта Linktery (основной домен: linktery.com),
структуры данных, интеграций и особенностей развертывания.

------------------------------------------------------------------------
1. ОБЩАЯ АРХИТЕКТУРА И СТЕК
------------------------------------------------------------------------

Проект построен по классической архитектуре SPA (Single Page Application) с разделением
на клиентскую часть (Frontend) и серверную часть (Backend) с базой данных:

*   FRONTEND:
    - Стек: React, TypeScript, Vite, Tailwind CSS.
    - Хостинг: Vercel (основной домен: linktery.com).
    - Запросы к бэкенду идут через REST API клиента PocketBase SDK.

*   BACKEND & DATABASE:
    - Стек: PocketBase (Go-сервер версии v0.24.4) с поддержкой JavaScript Hooks (Goja JSVM).
    - Хостинг: Fly.io (приложение `greenroute-pb.fly.dev` в регионе FRA / Франкфурт).
    - Базы данных (SQLite в WAL-режиме):
      * data.db (~800MB) — основная база (пользователи, ссылки, биллинг, промокоды, агрегированные клики).
      * auxiliary.db (очищена до 4KB) — вспомогательная база для хранения технических логов запросов PocketBase (таблица `_logs`).

------------------------------------------------------------------------
2. КАК ПРОХОДИТ ПОТОК ДАННЫХ (DATA FLOW)
------------------------------------------------------------------------

А) ПЕРЕНАПРАВЛЕНИЯ И СМАРТ-ССЫЛКИ (REDIRECTS & SMART LINKS)
1. Посетитель переходит по короткой ссылке (например, `linktery.com/username` или `linktery.com/r/link-slug`).
2. Frontend (React) принимает этот запрос и через роутер `RedirectHandler.tsx` или `SmartRedirect.tsx` обращается к PocketBase API.
3. PocketBase:
   - Ищет запись ссылки в коллекции `links`.
   - Запускает JS-хук в `main.pb.js`, который определяет страну посетителя (через заголовки Cloudflare `CF-IPCountry` / `Fly-Client-IP` с фоллбеком на внешний сервис IP-API.com).
   - Определяет устройство (мобильный/десктоп) и реферер.
   - Фиксирует клик в коллекции `clicks` (сохраняя IP, страну, устройство, браузер, ОС и дату).
   - Возвращает целевой URL на основе гео- и девайс-таргетинга или сплит-тестирования.
4. Браузер пользователя мгновенно перенаправляется на нужный URL.

*Оптимизация высокой нагрузки*:
Ранее аналитика строилась на динамических представлениях (SQL VIEW) над таблицей `clicks`, что при миллионах кликов вешало базу.
Сейчас внедрена физическая таблица `analytics_daily` (Rollup Table). При кликах данные инкрементируются в эту таблицу, и графики строятся по ней за миллисекунды. Скрипт `repair_db.py` на старте следит за целостностью этой таблицы.

Б) ПОДПИСКИ И БИЛЛИНГ (STRIPE INTEGRATION)
1. Пользователь в личном кабинете нажимает "Upgrade" (переход на тариф Pro или Agency).
2. Запрос отправляется на бэкенд на `/api/stripe/create-checkout`.
3. JS-хук в `main.pb.js`:
   - Ищет в коллекции `billing` (и таблице `users`) существующий `stripe_customer_id` пользователя.
   - Если ID найден — передает его в Stripe Checkout, предотвращая создание дубликата покупателя.
   - Если у пользователя уже есть активная подписка (например, Pro), её ID передается в метаданных сессии как `oldSubscriptionId`.
4. Пользователь оплачивает подписку на странице Stripe Checkout.
5. Stripe отправляет вебхук `checkout.session.completed` на `/api/stripe/webhook`.
6. JS-хук в `main.pb.js`:
   - Активирует новый тариф в коллекции `billing` (устанавливает статус, лимиты ссылок и дату окончания).
   - Если в метаданных есть `oldSubscriptionId` — хук делает запрос к Stripe API (`DELETE /v1/subscriptions/{id}`) и мгновенно отменяет старую подписку, предотвращая двойное списание средств при апгрейдах.

------------------------------------------------------------------------
3. ОСОБЕННОСТИ ИСПРАВЛЕНИЯ БАЗЫ ДАННЫХ И СТАРТА
------------------------------------------------------------------------

*   ПРОБЛЕМА ДИСКОВОГО ИМПОРТА (I/O HANG):
    Поскольку логи запросов PocketBase пишутся в `auxiliary.db` в таблицу `_logs`, этот файл разросся до 1.9GB.
    PocketBase при каждом старте пытается удалить старые логи (Log Rotation). На слабых виртуальных машинах Fly.io это вызывало 90% Disk I/O wait, лочило SQLite и приводило к тому, что порт 8080 не поднимался, а контейнер перезапускался по таймауту.

*   РЕШЕНИЕ:
    - Таблица логов `_logs` в `auxiliary.db` была полностью удалена (DROP TABLE) и база сжата с помощью команды `VACUUM` до 4KB.
    - В скрипт инициализации `pocketbase/repair_db.py`, который запускается при старте контейнера, добавлен принудительный сброс логов WAL (`PRAGMA wal_checkpoint(TRUNCATE);`) для обеих баз. Это гарантирует, что при перезапусках временные файлы транзакций SQLite (`-wal` и `-shm`) будут мгновенно слиты с основными файлами БД, предотвращая зависание фазы WAL-recovery.

------------------------------------------------------------------------
4. ЛОКАЛЬНЫЙ ЗАПУСК И УПРАВЛЕНИЕ ДЕПЛОЕМ
------------------------------------------------------------------------

*   ЛОКАЛЬНЫЙ ФРОНТЕНД:
    1. Установите зависимости: `npm install` или `bun install`.
    2. Скопируйте `.env` файл и укажите URL локального или тестового бэкенда.
    3. Запуск: `npm run dev`.

*   ДЕПЛОЙ ФРОНТЕНДА:
    Деплой происходит автоматически при пуше в ветку `main` на GitHub через интеграцию с Vercel.

*   ДЕПЛОЙ БЭКЕНДА (POCKETBASE):
    1. Все хуки бэкенда лежат в `pocketbase/pb_hooks/main.pb.js`.
    2. Все миграции БД лежат в `pocketbase/pb_migrations/`.
    3. Накатите изменения локально или отправьте на GitHub.
    4. Для деплоя на Fly.io перейдите в папку `pocketbase` и выполните:
       `fly deploy --app greenroute-pb`
    5. При деплое автоматически соберется Docker-образ, запустится `repair_db.py` (сбросит WAL) и запустится актуальный PocketBase.
